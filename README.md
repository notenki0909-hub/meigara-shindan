# 銘柄診断ツール v1（日本株）

証券コードを1つ渡すと、その銘柄を **銘柄選定スコア** と **買い時スコア** の
2本立てで自動評価し、**HTMLレポート（＋Markdown）** を書き出します。

- **銘柄選定スコア**（0〜110）＝長期保有できる配当株か。業績（売上増減率・EPS増減率・営業利益率・**利益の安定度**）／財務（自己資本比率・D/E・ネットD/E・負債÷営業CF）／キャッシュフロー／配当の持続力（増配率・連続増配・非減配・配当性向・ROE・**累進配当/DOE宣言**）
- **買い時スコア**（0〜110）＝今エントリーする価値があるか。配当利回りセオリー（自分の過去レンジ内の位置）／利回り水準＋Chowder／株価バリュエーション（対業種平均PER・PBR＋**PERの自社過去レンジ内の位置**）／**利回り−10年国債スプレッド**（金利敏感セクターのみ）。RSI等テクニカルは採点せず参考のみ

2つを quality×timing の象限で読んで一言コメントを出す（例：選定◎×買い時▲＝「長期保有できる銘柄だが今は割高。ウォッチリスト入り、押し目を待つ」）。総合スコアは廃止（2つを混ぜると「良い会社か」と「今買うか」が区別できなくなるため）。

配当金投資.txt の「判断材料5層」「東証33業種の平均指標」をコード化したもの。

---

## 使い方

```bash
python analyze.py 9433                 # KDDI を診断
python analyze.py 9433 --cost 3000     # 取得単価を入れると YOC も計算
python analyze.py 8058 --name 三菱商事  # 会社名を明示（省略時は yfinance の名称）
python analyze.py 8306 --no-irbank     # IR BANK 補助を使わない
```

出力先: `out/<コード>_<会社名>.html` と `.md`

レポート冒頭に「現在株価 X円（YYYY-MM-DD 終値）」＝どの営業日の終値かを表示。
週末・休場明けはレポート作成日と数日ずれることがある。

## 依存

```bash
python -m pip install yfinance
```

`requests`（IR BANK 補助）は任意。無ければ自動でスキップ。

## データ源

| 用途 | ソース | 備考 |
|---|---|---|
| 株価・財務3表・配当・PER/PBR 等 | **yfinance** | 無料・キー不要・遅延なし。非公式なので取得失敗あり。配当は20年超さかのぼれる |
| 連続増配年数・5年増配率 | yfinance の配当を**会計年度換算**（4月始まり・支払回数が異常な年＝特殊配当は除外・分割調整のゆらぎは橋渡し） | IR BANK スクレイプは best-effort（現状ほぼ失敗）で、成功時のみ優先 |
| 業種の特定 | yfinance の industry / sector → `sector_map.json` で東証33業種へ変換 | GICS 由来なので1対1でない＝近似 |
| 業種平均・判定しきい値 | `sector_averages.json` / `sector_rules.json` | **2026年8月時点のスナップショット** |

> **連続増配の限界**：yfinance の JP 配当データは15年以上さかのぼると分割調整・特殊配当で崩れがち。12年以上の連続増配は `NN年＋` と表示し「実際はより長い可能性」と注記する（花王＝実35年→表示13年＋ 等）。より正確な決算期ベースが要るなら **J-Quants スタンダード（¥3,300/月・10年）** または **EDINET DB 無料枠**（`X-API-Key`・100req/日・`/v1/companies/{EDINETコード}/financials`）を後付けする（現状は不要と判断）。

## 業種で判断基準を切り替える仕組み

`sector_rules.json` =「`default`（全業種共通の土台）＋ `overrides`（その業種だけ上書き）」。
各指標を `{dir, good, warn, bad}` で持ち、業種キーで上書きする。未定義の業種は default をそのまま使う。

例:
- 配当性向の健全域 … 一般 0〜50% / 電気・ガス・情報通信・鉄道 0〜70% / 卸売 0〜40% / 海運 0〜35%
- Chowder 閾値 … 一般 12% / 公益・通信・鉄道・その他金融 8〜10%
- 自己資本比率の下限 … 一般 40% / 不動産 28% / その他金融 15%
- 増収・増益率の警戒ライン … 売上 −6% / 利益・EPS −8%（景気敏感株が“ピーク後の正常化”で不当に低評価されないよう、0%ではなく小幅マイナスを許容。2026-09-03 の校正で調整）
- 銀行・保険・証券・REIT … `_simple: true`（`score_groups.simple_excludes`）。業績・財務・CF は**採点から外す** → 銘柄選定スコアは「配当の持続力」グループのみ、買い時スコアは通常どおり

しきい値を変えたいときは JSON を直すだけ（コード変更不要）。

## スコアの出し方

1. 各指標の点は **`good` / `warn` の2閾値の間を直線補間**（階段ではなくスロープ）
   - `warn` → 60点、`good` → 100点、その間は直線
   - `good` の外側は `good ± (good−warn)` の「別格ライン」まで 100→110 で微加点（上限110）
   - `warn` の内側は `warn −(good−warn)` で 20点に着地、それ以降フラット20
   - band 型（配当性向など）は健全域=100（別格加点なし）、warn帯を100→60、その先20へ
   - `営業CF±` など2択の指標は 100 / 20 のまま
2. グループスコア = そのグループの採点済み指標の点の平均（最大110）。グループ＝`sector_rules.json` の `score_groups`
3. **銘柄選定スコア** = 業績28・財務27・CF15・配当の持続力30％ の加重平均（取得できたグループだけで正規化）
   **買い時スコア** = 配当利回りセオリー38・利回り水準とChowder24・株価バリュエーション20・金利スプレッド18％ の加重平均
4. サブ表示 … 割安・割高（PER・PBR の対業種平均＋配当利回りの過去レンジ内の位置を合成、±0.5クランプ）／成長性（増収・増益率）／安定性（財務＋CF）／参考・短期（RSI・MACD、採点対象外）
5. **カバレッジ** … 各スコアの下に「採点できた指標 N/M ・カバレッジ 高/中/低」を表示。M＝その銘柄・業種で本来採点する指標数（構造的にN/Aな指標＝簡易判定の除外グループ・金利敏感外の金利スプレッド、および宣言なしで正常にNoneになる累進配当は分母から除外）。カバレッジ **低（65%未満）** のときは冒頭に警告、総合コメントの頭に「※データ不足・参考程度」を付ける。履歴不足は主に **銘柄選定** 側に効く（yfinanceの財務が約4期）。買い時は株価履歴中心なので影響が小さい。

### 判定ラベルの段階

- 指標ごとの**ラベルは3段階**：`◎ 良好`（値が `good` を満たす）／`△ 注意`（`warn` は満たすが `good` 未満）／`▲ 弱い`（`warn` 未満）＋ 対象外 `―`
- ラベルは閾値そのもので決まるので、**ラベルと点がずれる**ことがある（例：D/E 1.14倍 → `△ 注意`（基準1.0倍を僅かに超過）だが点は 94）。これは「基準ぎりぎりか大幅アウトか」を1行で示すための仕様。
- **銘柄選定** の4区分（`analyze.py` の `SEL_TIERS`。2026-09-04、日本の代表的な配当・優良17銘柄で校正。分布 min65／中央値88／max102）：
  **85+** 長期保有できる配当株（12銘柄）／**68+** 及第点（4）／**55+** 質に不安あり（1）／55未満 基準を満たさない（0）
- **買い時** の4区分（`TIM_TIERS`。分布 min53／中央値62／max103、市場全体が割高寄りのため低め）：
  **72+** 買い場（割安圏）（3銘柄）／**57+** ほぼ妥当（11）／**45+** やや割高（3）／45未満 割高で見送り（0）
- 安定性ラベルは 88 / 68。校正バッチ＝`scratchpad\batch_calib.py`

### レポートの各行はクリックで開く

HTMLレポートの明細は各行が折りたたみ。クリックすると
**見るポイント**（その指標の意味）／**判定ルール**（その業種のしきい値）／
**この銘柄がその評価になった理由**（値 vs ライン）が展開される。
Markdown 版は各行の「判定・根拠」列に同じ理由文が入っている。

「① 銘柄選定の指標」の先頭に **「指標スコアを一覧グラフで見る」** の折りたたみ。
クリックすると全指標の点（0〜110）を横棒で一覧表示（グループ別・△60/◎100 の
破線つき・右に実値）。強い/弱い指標が一目で分かる（`svg_score_bars`）。

**過去からの推移がある指標**は、行を開くと **推移の折れ線グラフ**（古い→
新しい・**y軸目盛りつき**・年ラベル・端点に実値・負値は0基準線つき）も表示される（`svg_trend`）。
対象＝売上高・EPS・営業利益・純利益・税引前利益・営業CF・投資CF・財務CF・
フリーCF（億円/兆円表示）／**営業利益率・自己資本比率・配当性向・予想配当利回り**（％表示）。

うち **営業利益率・自己資本比率・配当性向・予想配当利回り** は判定ルールと単位が
一致するので、グラフに **◎良好／△注意／▲弱いの帯（ゾーン）＋境界線** を重ねる。
配当性向・予想配当利回りは行の値（yfinance予想/TTM）を「▶ 現在」点で明示。

**自社の過去レンジで位置を測る指標**（配当利回りセオリー・予想配当利回り・
PERの自社過去レンジ位置）は、行を開くと **RSI風のレンジ帯グラフ**（`svg_rangeband`）。
過去レンジを 低/標準/高 の3ゾーンに塗り分け（利回りは上が割安・PERは下が割安）、
年次履歴の折れ線と「▶ 現在」マーカー、**y軸目盛り**、ヘッダーに「割安度 NN%」を表示。

株価チャート（上部）と1株配当チャートにも y軸目盛り（`nice_ticks`／`_yscale`）。

## 直近決算とアナリスト予想（採点しない・文脈情報のみ）

推移チャートの下に **「直近決算とアナリスト予想」** セクションを表示（`build_earnings` ／
`render_earn_html` ／ `render_earn_md`）。スコアには一切反映しない。出典は yfinance
（Yahoo Finance）で、**日本株は対象アナリストが少なく予想が古い・欠損しやすい**旨を
セクション冒頭に明記。取れた項目だけを出し、無い項目は行ごと省略する。

| 行 | 中身 | ソース |
|---|---|---|
| 直近決算 EPS | 実績EPS・事前予想EPS・サプライズ%・開示日。四半期EPSが開示EPSとほぼ一致するとき（±2%）は前年同期比を同じ行に添える | `earnings_dates`（Reported EPS / EPS Estimate / Surprise(%)）|
| 直近四半期 | 米国株など四半期損益が5列以上あるときのみ 売上・営業利益・純利益の前年同期比。日本株は四半期 `Diluted/Basic EPS` の前年同期比（2列）で代替 | `quarterly_income_stmt` |
| 決算の評価（機械判定） | 「増収増益／減益」＋「市場予想を上回る／下回る／ほぼ予想どおり」（サプライズ ±5%）を機械的に連結。データ不足なら「判定に必要な…不足」 | 上2行から導出 |
| 今後の見通し（アナリスト予想） | 今期・来期の予想EPS・前期比・予想PER（＝現在株価÷予想EPS）・アナリスト数、今期予想売上 | `earnings_estimate` / `revenue_estimate`（`0y` / `+1y`）|
| 次回決算 予定日 | 未報告の決算日、無ければ `calendar` | `earnings_dates` / `calendar` |
| アナリスト目標株価 | 平均・現在株価比・高値/安値 | `analyst_price_targets`（無ければ `info.target*Price`）|
| アナリスト・レーティング | 強気買い〜売りの和訳・平均スコア（1=強気/5=弱気）・対象数 | `info.recommendationKey` / `recommendationMean` |

- `info["forwardEps"]` / `forwardPE` は日本株で壊れていることがあるので**使わない**。予想EPSは
  `earnings_estimate` の `0y` / `+1y` の平均を使う。
- 予想の前期比（`growth`）は yfinance 内部の前年実額推定がずれて桁違いになることがあるため
  **±60% を超えたら表示しない**（`_g()`）。
- 「今後の見通し」は**アナリストのコンセンサス**であって会社予想ではない。会社の正式な
  業績予想は決算短信・決算説明資料で確認すること（セクション冒頭にも注記）。

## 減配履歴（2026-09-05追加）

「参考」欄に **減配履歴** を追加。`find_last_cut()` が「連続非減配年数」と同じ判定
ロジック（0.5%超の下げ＝実質減配）で、直近の実質減配があった会計年度を特定して表示する。

- 過去の減配は**恒久的な減点にはしない**方針。実際の採点は既存の2つの指標で行う：
  - `streak_flat`（連続非減配年数＝直近の減配からの経過年数）が good=15年／warn=5年の
    直線補間で採点されるため、減配から時間が経つほど自然にスコアが回復する
  - `div_policy`（累進配当・DOE宣言）は減配歴の有無に関係なく別枠で加点
- 「減配履歴」欄はこの**裏側の事実を可視化するだけ**（新しいスコアは追加していない＝
  二重評価を避けるため）。表示は4パターン：減配歴なし／減配歴あり＋累進配当宣言で
  現在は良好／その後10年以上減配なしで良好水準／5〜9年で回復途上／5年未満で要注意。

## 業績・財務の推移データの期間について（2026-09-05）

各指標の「年率」表記は `（直近N期のデータから算出）` に統一（以前は「N期」がCAGRの
計算区間数を指していて、データ点数と誤認されやすかった）。**yfinanceの年次財務データは
JP株で最大4期分が上限**（Yahoo Finance側のデータ提供の壁で、コード側の制限ではない）。
5期以上にするには J-Quants Standard（¥3,300/月・10年分）または EDINET DB（無料・
第三者提供・6年分程度）の追加導入が必要（現状は不要と判断・継続検討事項）。

## 採点しない項目（レポートの「参考」欄）

- 配当の中身（記念・特別配当）… 直近3年で通常の1.8倍超の回があれば「混在の可能性」とフラグするだけ
- 累進配当・DOE の方針 … `dividend_policy.json` の手管理リストで判定（宣言ありなら加点、なしは減点しない）。**会社の最新開示で要確認・年1見直し**。リスト外の一次情報リンクは「参考」欄に
- 営業利益・純利益の増減率／有利子負債比率／現金比率 … それぞれ EPS増減率・D/E と重複、または予測力が弱いため参考へ降格
- ROIC … 業種中央値が新興企業で歪む（情報通信・医薬）ため採点対象外。絶対ROEで見る
- RSI・MACD・スローストキャス … 短期すぎるため採点対象外。買うタイミングの参考のみ

## 10年国債利回り（金利スプレッド用）

- `sector_rules.json` の `market.jgb_10y`（同梱値、四半期ごとに手更新）。実行時に stooq から best-effort 取得を試み、取れればそちらを使う。`--jgb 1.7` で明示指定も可。
- 金利スプレッドを採点するのは `sector_map.json` の `_meta.rate_sensitive` にある業種（公益・通信・不動産・鉄道・食料品・医薬・小売）だけ。

## Web一般公開版（バッチ生成＋静的サイト）

「利用者はサーバーが用意したリストの中から証券コードを選び、毎晩バッチ生成済みの
レポートを見る」構成。サーバーはリクエスト時に yfinance を叩かないので、
クラウドIPのブロック問題が起きない。GitHub Pages / Cloudflare Pages で成立。

```bash
# 0. ユニバースを作る（四半期に1回。universe-quarterly.yml で自動化済み）
#    JPX の「東証上場銘柄一覧」を落とす（月末更新）:
#    https://www.jpx.co.jp/markets/statistics-equities/misc/01.html
#    2026-09時点は data_j.xlsx（openpyxlでそのまま読める。直接URL:
#    .../misc/tvdivq0000001vg2-att/data_j.xlsx を curl 可・実データで動作確認済み）。
#    旧形式の .xls を渡された場合はこの環境で直読みできないので、Excel で開いて
#    CSV(UTF-8) か .xlsx で保存し直す。
python build_universe.py candidates --jpx data_j.xlsx   # 市場区分＋ファンド除外 → universe_candidates.json
python build_universe.py screen --sleep 1.5             # 利回り/時価総額/減配なし を yfinance で適用 → universe.json
python build_universe.py all --jpx data_j.xlsx --sleep 1.5   # 上2つを続けて
python build_universe.py screen --resume                # 途中から/差分だけ

# 1. ユニバースの全銘柄を診断（レポート＋サマリJSONを書き出す）
python batch.py --codes universe.json --sleep 1.5
python batch.py --codes 9433,8058,2914          # 直接指定も可
python batch.py --codes universe.json --only-stale --hours 20   # 古い分だけ

# 2. サマリから軍分けランキングと一覧ページを作る
python rank.py
```

出力先 `site/` :

| パス | 中身 |
|---|---|
| `site/reports/<code>.html` `.md` | 個別レポート（`analyze.py` 単体実行と同じ内容） |
| `site/summaries/<code>.json` | ランキング集計用のフラットなサマリ＋生成時刻 |
| `site/ranking.json` | 業種級・軍・方向フラグ付きの集計結果 |
| `site/index.html` | グループ別ランキングページ（軍の色分け・全体上位50・各行から個別レポートへリンク） |
| `site/batch_log.json` | 直近バッチの ok/fail 件数と失敗コード |

**軍分けの仕組み**（`sector_groups.json`）：東証33業種を配当株向け12グループへ集約し、
グループ内で銘柄選定スコアの高い順に **上位25%＝1軍／次45%＝2軍／残り＝3軍**。
カバレッジ「低」は最高でも2軍。グループの対象が6銘柄未満なら軍分けせずフラット表示。
**絶対スコアの下駄**：銘柄選定スコアが `analyze.py` の `SEL_TIERS[0]`（85＝長期保有できる
配当株）以上なら、強いグループに属しているだけでグループ内パーセンタイルで3軍に落ちない
よう最低2軍を保証（1軍は据え置き＝グループ内上位という意味を残す）。
**業種級 A/B/C** はグループ内の銘柄選定スコア中央値（`grade_a`/`grade_b`）。金融（簡易判定）は
自動的に独立グループになり事業会社と混ざらない。**方向フラグ ↑改善中／→／↓悪化中** は
前回 `ranking.json` との選定スコア差（±2）。

> `grade_a`/`grade_b` はスクリーン済みユニバースの実分布で校正する数値（初期値80/68は
> 無フィルタ想定で外れていたため、2026-09-04 の677銘柄ランで 94/91 に再校正済み）。
> ユニバースの条件やNが変わったら `sector_groups.json` の校正メモに沿って見直すこと。

**ユニバースのスクリーン条件**（`universe_screen.json`）：東証プライム＋スタンダードの
内国株式／予想利回り≥2.0%／時価総額≥300億円／直近5年 減配なし（累進配当・DOE宣言＝
`dividend_policy.json` 掲載は例外）／REIT・ETF・グロース・外国株を除外。四半期ごとに見直し
（上場廃止・被買収は即除外）。

`build_universe.py` の流れ：
1. `candidates` … JPX `data_j`（CSV/xlsx）の「市場・商品区分」で内国株プライム/スタンダードだけ
   残し、ファンド類を落とす（ネットワーク不要）。コードは4桁に正規化。→ `universe_candidates.json`
2. `screen` … 各候補を yfinance の `history`（7年・1回）で軽く取得し、trailing利回り・
   時価総額（`fast_info`）・非減配年数（`analyze` の DPS 集計を再利用）で数値スクリーン。
   → `universe.json`（`codes`＝通過、`rejected`＝除外理由つき）。`--resume` で差分実行。

## 決算翌日反映（TDnet検知）

決算発表を検知したら、その銘柄だけ優先的に再取得して yfinance 側の反映を待つ仕組み。
2本のスクリプトで検知と反映確認を分担する。

```bash
# 検知（平日11:00〜17:00 JSTの間、30分おきの実行を想定。GitHub Actions cron未実装）
python tdnet_watch.py                    # 今日ぶんをポーリング
python tdnet_watch.py --date 20260805    # 過去日を指定（取りこぼし確認・テスト用）

# 反映確認・再取得（6時間おきの実行を想定）
python earnings_retry.py                 # 期限が来たものだけ処理
python earnings_retry.py --status        # 監視中一覧を見るだけ
python earnings_retry.py --force         # 期限無視で全件処理（テスト用）
```

仕組み：
1. `tdnet_watch.py` が TDnet（適時開示情報）の当日一覧を第三者ミラー
   （`webapi.yanoshin.jp/webapi/tdnet/list/`）から取得し、タイトルに「決算短信」を含み
   かつ `universe.json` のユニバース内の銘柄だけを `pending_earnings.json` に積む
   （訂正・決算説明資料・業績予想の修正は「決算短信」を含まないので自然に除外）。
2. `earnings_retry.py` が pending を6時間おきに再取得（`analyze.generate()` を素通し）し、
   yfinance の実績開示日（`earn_disc_date`）がTDnetの開示日以降に進んだら「反映」と判定して
   `site/reports/` `site/summaries/` を更新、監視終了。まだなら次回+6時間で最大9回
   （約3日）リトライし、それでも反映されなければ週次のフルバッチに委ねて監視終了。
3. 古い完了分（resolved/giveup）は14日で自動整理。

実データで動作確認済み（2026-09-04）：本日のTDnet開示170件からユニバース内の決算短信を
2件検知、`--force` 再取得は未反映（yfinance反映前）を正しく検出、合成テストで反映済み
判定〜ファイル更新も確認。

## GitHub Actions（自動実行）

`.github/workflows/` に4本。**この`銘柄診断ツール`フォルダ自体を独立したGitHubリポジトリ**
にする前提（親の `AI道場` フォルダには他の教材等が混在するため、そこごと公開しない）。

| ワークフロー | 頻度 | やること |
|---|---|---|
| `nightly.yml` | 毎晩 03:00 JST | `batch.py --only-stale --hours 20` → `rank.py` → mainへコミット |
| `tdnet-watch.yml` | 平日 11:00〜17:30 JST・30分おき | `tdnet_watch.py` → mainへコミット |
| `earnings-retry.yml` | 6時間おき | `earnings_retry.py` → `rank.py` → mainへコミット |
| `universe-quarterly.yml` | 1/4/7/10月の1日（目安）＋手動 | JPXの `data_j.xlsx` を取得 → `build_universe.py all` → 全銘柄診断 → **PRを作成**（銘柄の出入りは人間が確認してからマージ。直接mainには入れない） |

セットアップ手順：

```bash
cd 銘柄診断ツール
git init
git add .
git commit -m "init"
git branch -M main
git remote add origin <あなたのGitHubリポジトリURL>
git push -u origin main
```

GitHub側でリポジトリの Settings → Actions → General → Workflow permissions を
「Read and write permissions」にする（`github-actions[bot]` がmainへpushするため）。
シークレットは不要（yfinance・JPX・TDnetミラーはすべて認証なしの公開API）。
`main` にブランチ保護（PR必須など）を掛けている場合、nightly/tdnet-watch/earnings-retry の
直接pushが弾かれるので、保護しないか、この3本だけ例外にする必要がある。

JPXのダウンロードURL（`universe-quarterly.yml` 内）はページ構造が変わると壊れる可能性がある。
四半期ジョブが失敗したら https://www.jpx.co.jp/markets/statistics-equities/misc/01.html
で最新のURLを確認してワークフローを直す。

## Cloudflare Pages 公開

`site/` はビルド不要の完成済み静的ファイル（HTML・画像はSVGインライン埋め込み）なので、
**Cloudflareダッシュボードの Git連携だけ**で公開できる。GitHub Actions側の変更は不要
（Cloudflareの連携はGitHub Appのpush Webhookで動くので、`GITHUB_TOKEN`でも
Personal Access Tokenでも関係なく反応する）。APIトークン等のシークレットも不要。

前提：先に「GitHub Actions（自動実行）」節の手順でこの`銘柄診断ツール`フォルダを
GitHubへpush済みであること。

1. Cloudflareダッシュボード → **Workers & Pages → Create → Pages → Connect to Git**
2. さっき push したリポジトリを選択
3. ビルド設定：
   - Framework preset: **None**
   - Build command: **（空欄のまま。何も入力しない）**
   - Build output directory: **`site`**
   - Root directory: `/`（リポジトリ直下＝この`銘柄診断ツール`フォルダがそのままrootの想定）
4. Save and Deploy → 初回は今ある `site/` がそのまま公開される
5. 以降は `main` に `site/` を含むpushがあるたび自動で再デプロイ（nightly/tdnet-watch/
   earnings-retryのコミット、universe-quarterly のPRをマージした時も含む）
6. `universe-quarterly-update` ブランチのPRにも自動でプレビューURLが付くので、
   マージ前に新しいユニバースの見た目を確認できる
7. 独自ドメインを付けたい場合は Pages プロジェクトの Custom domains から追加（任意）

**容量の目安**（Cloudflare Pages Freeプラン）：ビルド 500回/月・ファイル数 20,000・
1ファイル25MiBまで。現状677銘柄で約2,000ファイル・66MB＝ファイル数の余裕は大きい。
デプロイ回数は「pushの回数」なので、nightly毎日約1回＋決算シーズンのtdnet-watch/
earnings-retryのバースト＋四半期のuniverse-quarterly統合を足しても月60〜100回程度の
見込みで500回に対して十分余裕がある（tdnet-watch/earnings-retryは変化があった時しか
コミットしないため）。ユニバースを大きく増やしてファイル数が万単位に近づく場合は
`.md`/`summaries/`を非公開の別ディレクトリへ分離するなどの見直しが要る（未実装）。

ローカルで見た目だけ確認したい場合：`npx wrangler pages dev site`（`wrangler.toml` 同梱）。

`analyze.py` はライブラリとしても使える：

```python
import analyze
r = analyze.generate("9433", jgb=1.6)      # {"ok","html","md","summary",...}
```
